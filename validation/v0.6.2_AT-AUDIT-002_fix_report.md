## 1. 问题根因

审计报告指出的位置 `result_store.py:39-41` 经核对**属实**（现为 `record()` 的 append-only 实现），但污染并非只由 events 造成，而是**三个因素叠加**：

| # | 根因 | 证据（修复前） |
|---|---|---|
| **R1** | `RunEvent` **没有任何任务归属字段** —— 只有 `agent_id/event/timestamp/message` | `result_store.py:22-26`（修复前） |
| **R2** | `record()` 只向单一扁平列表 append，**永不清理**；`status_of()` 遍历**全部历史**事件 | `result_store.py:39-41`、`67-80`（修复前） |
| **R3** | `status_of()` 的**第一条分支**先查 `self.results`，而 `set_results()` 是整表覆盖 —— 上一次 run 的 results 会残留到下一次 run 启动后 | `result_store.py:69-71`、`54-56`（修复前） |
| **R4** | `ResearchOrchestrator` 持有 `self.store = store or ResultStore()`，**跨 `run()` 调用复用同一 store**，且 `run()` 从不绑定/区分 run | `orchestrator.py:46`、`55-69`（修复前） |
| **R5** | 事件缺少 run_id 的**直接原因**：`AgentRuntime` **早已接收** `run_id` 参数并存为 `self.run_id`，但三处 `store.record(RunEvent(...))` **从未把它写进事件** | `agent_runtime.py:196/209` vs `:823/:894/:905`（修复前） |

**因此污染路径有两条**（R3 的 results 泄漏 + R2 的 events 泄漏），且 R4 提供了长期存活的 store，R5 导致事件无身份可区分。

### 1.1 旧实现的稳定复现（实测）

对同一 store：run A 以 `writer=SUCCESS` 结束 → run B 启动（B 侧尚无事件），查询 `writer` 状态：

```
OLD status_of during run B : success   <-- 泄漏自 run A（经 self.results 残留）
NEW status_of(writer, B)   : pending   <-- 修复后：只看 run B
NEW status_of(writer)      : pending   <-- 默认 = 当前绑定的 run B
NEW status_of(writer, A)   : success   <-- run A 自身不受影响
run A events preserved     : 2         <-- 未删除任何数据
```

> 旧逻辑在上述场景下**必然**返回 A 的 `success`（因为 `self.results` 仍持有 A 的结果），这是确定性的、可稳定复现的，而非偶发时序问题。

## 2. 修复前调用链

```

  └─ self.store = store or ResultStore()        ← 长生命周期单例
       └─ AgentRuntime(store=self.store)        ← 未传 run_id ⇒ self.run_id = ""

  ├─ store.set_structure(...)                   ← 覆盖式

  └─ store.set_report(...)

orchestrator.run()（第 2 次，同一 store）      ← 无任何 reset / 绑定
  ├─ store.set_results(results2) 之前：
```

**不受影响的路径（已核实）**：`session.py:177` 每次 `execute_task` 都 `store=ResultStore()`（新建），因此 FastAPI / SSE / Session 主链路**本就不跨 run 累积**——这也是该缺陷能潜伏到发布候选的原因之一。

## 3. 修复方案

原则：**分区（partition），绝不清理（no clearing）**；保留原有数据结构与对外接口；不引入 DB/Redis/新框架。

### 3.1 事件具备可验证的任务归属

`RunEvent` 新增字段（默认 `""`，旧构造方式完全兼容）：

```python
class RunEvent(BaseModel):
    agent_id: str
    event: str
    timestamp: float
    message: str = ""
    run_id: str = ""      # v0.6.2 (AT-AUDIT-002)
```

`AgentRuntime` 三处 `record` 站点改为透传**已存在的** `self.run_id`（`agent_runtime.py:830 / 902 / 914`）——这是最薄的一层，未改动事件架构，也未改 `execute` 签名。

### 3.2 ResultStore 按 run 分区

| 新增/改造 | 行为 |
|---|---|
| `_events_by_run: dict[str, list[RunEvent]]` | 事件按 run 归档（与 `events` 共享同一对象引用，非深拷贝） |
| `_results_by_run: dict[str, dict[str, AgentResult]]` | results 按 run 归档 |
| `current_run_id: str \| None` | `start_run()` 绑定的当前 run |
| `start_run(run_id)` | 绑定当前 run，**只 setdefault 不清理** —— 其他 run 数据分毫不动 |
| `record(event, run_id=None)` | 归属优先级：显式参数 → 事件自带 → 当前绑定 run；空则回填 `run_id` |
| `set_results(results, run_id=None)` | 写入对应 run 分区，同时保留 `self.results`（兼容） |
| `status_of(agent_id, run_id=None)` | 显式 run_id → 严格只查该 run；省略 → 当前绑定 run；**从未绑定过 run 的 store → 返回历史聚合视图（100% 兼容）** |
| `events_of(run_id)` / `runs()` | 取某 run 的事件（保持写入顺序）/ 列出所有 run |
| `snapshot(run_id=None)` | 传 run_id → 该 run 切片；否则沿用旧行为 |

**关键设计点**：状态查询**不依赖「最近一个任务」或全局最新事件**，而是按显式 run 分区；并发下每个 `record` 自带 run_id，天然隔离。

### 3.3 并发安全

`_lock` 升级为 `threading.RLock`（避免同类方法重入），所有分区读写均在锁内。

**为什么不给共享 runtime 直接改 `run_id`**：`runtime.run_id` 是全局可变状态，两次 `run()` 交错时会互相覆盖——正是本次要消除的那类 bug。因此 orchestrator 改为**每次 run 构造一个绑定该 run_id 的 runtime**（配置相同，仅 run_id 不同）：

```python
def _runtime_for(self, run_id: str) -> AgentRuntime:
    kwargs = dict(self._runtime_kwargs); kwargs["run_id"] = run_id
    return AgentRuntime(**kwargs)
```

`run()` 开头：`run_id = self.store.start_run(f"run_{uuid.uuid4().hex[:8]}")`，并以 `set_results(results, run_id=run_id)` 归档。

- `AgentRuntime.execute` 签名与重试/工具逻辑：**未改**

## 8. 剩余限制

1. **`structure` / `report` / `done` / `error` 仍是覆盖式（未按 run 分区）**。本次只修复 AT-AUDIT-002 的核心（事件归属 + 状态隔离）；对复用 store 的场景，快照中的 structure/report 仍反映**最近一次** run。如 Live View 需要严格按 run 显示结构，需另行扩展（不在本次范围）。
2. **`ui_dynamic.py:156` 仍调用无参 `snapshot()`**。该页面每次点击都会 `ResultStore()` 新建（`:148`），因此实际不跨 run；但严格来说未显式传入 run_id，若将来改为复用 store 需一并调整。
3. **并发同一 orchestrator 实例**：本次已通过「每 run 独立 runtime」消除 run_id 竞态；但 `structure/report` 仍是共享覆盖字段（见第 1 条），两个 run 真正并发时**结构字段仍会互相覆盖**——属剩余限制，非本次引入。
4. **内存增长未被彻底消除**：分区解决了「状态串味」，但完成 run 的分区仍驻留内存（无 TTL/LRU 淘汰）。**这是刻意保留**——清空会违反「不误删其他正在执行任务的数据」。彻底的回收需配合 `AT-AUDIT-010`（Registry 无界增长）一并设计淘汰策略，不在本次范围。
5. `status_of` 在**从未绑定 run** 的 store 上仍返回历史聚合视图——这是**刻意的向后兼容**，也是旧语义的保留；新代码应显式传 `run_id`。
