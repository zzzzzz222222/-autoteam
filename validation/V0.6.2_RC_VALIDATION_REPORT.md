## 2. Change

一处文件，`+82 / −8`：**`validation/collect.py`**。不是架构改动，是给既有的 finding 序列化补上一个它漏掉的字段。

```
validation/collect.py | 90 ++++++++++++++++++++++++++++++++++++++++++++++-----
```

### 2.1 实际修的是什么（需要先纠正一句此前报告的话）

我在 AT-AUDIT-004 报告的 Known Limitation #1 里写过：

> `collect.py` 序列化 finding 用显式字段元组，不含 `support_audit` → 从已落盘 `synthesis.json` 重算 `citation_verified` 恒为 0。

**这句话不准确。** 本次追查链路后确认：完整的 `support_audit` **一直被持久化**在 `synthesis.json → claim_audit[]`（由 `synthesizer.py:546-556` 按 `finding_id` 写入，全量字段），并在 `synthesis_audit.json` 里也有一份。

真正的缺口比"完全没存"要窄，也更具体：

> `support_audit` 存在，但**没有挂在 finding 行上**。离线复核者必须知道"要去 `claim_audit` 里按 `finding_id` join"这层隐含知识；按最自然的方式（读 `findings[]` 重建 Finding）重建，`citation_verified` 静默变成 0，而 `total` / `supported` / `backed_count` 全都对得上——**错误是静默的**。

### 2.2 修法（最小向后兼容扩展）

复用现有对象结构，不创建第二套 support model：

| 新增 | 位置 | 作用 |
|---|---|---|
| `FINDING_AUDIT_FIELDS` | `collect.py:29` | 明确列出要投影的 5 个键 —— 全是 `audit_claim_support()` 原本就写在 `Finding.support_audit` 上的键：`status`、`numeric_check`、`numbers_supported`、`numbers_missing`、`scope_flags` |
| `dump_finding_audit(item)` | `collect.py:375` | 写侧：投影 + 复用 `redact_text`（与 `_dump_items` 同一套脱敏规则）。无审计时输出 `{"available": False}`，**不冒充"已核验"** |
| `restore_finding_audit(row, claim_audit)` | `collect.py:400` | 读侧：先用行内投影；没有则回落到 `claim_audit` 按 `finding_id` join（旧产物路径）；都没有则返回 `{}`（= 未核验，永不等于已核验） |
| 行内附加 | `collect.py:497` | `_synthesis()` 把 `row["support_audit"] = dump_finding_audit(item)` 挂到每条 finding |

原字段**一个没动**：`findings[]` 里既有的 14 个键全部原位保留，只在行尾追加一个键。旧 reader 直接 `.get()` 或忽略即可。

### 2.3 为什么是投影而不是整个 dict

在同一个真实产物（`20261003T084253Z_A_real`，10 findings）上实测：

| 方案 | 体积 |
|---|---|
| 投影（5 键） | **1,935 字节**（均值 193.5 B/finding） |
| 整个 `support_audit` 内联 | 27,689 字节 |

14 倍差距。全量审计（`checks` / `witnesses` / `uncited_candidates`）**本来就已经**在 `claim_audit` 与 `synthesis_audit.json` 里，没有必要在 `findings[]` 里再抄一遍 —— 这也和仓库里既有的 `_selection_summary()` 做法一致（"全文放在 `synthesis_audit.json`，本文件保持可读"）。

### 2.4 明确没做的事

未改 `claim_support()` 的算法；未引入 LLM Judge；未加语义相似度模型；未改 `source_text` / `agent_consensus` / `derived` 的任何语义；未动 `synthesizer.py`（AT-AUDIT-004 的 `SUPPORTED_LEVELS` / `INTERNAL_BACKING_LEVELS` / `CITATION_VERIFIED_STATUS` / `compute_finding_counts()` 全部原样保留）；未改前端；未碰 core / scheduler / evidence / artifact。

## 11. Known Limitations

1. **本轮 Real Scenario A/B 未执行**（闸门阻断）。因此"AT-AUDIT-004 修复后在**新真实运行**中的数据链路"尚未端到端实跑过；现有结论建立在 12 项合成往返测试 + 23 个历史真实产物的离线重算之上。修复与缺陷复现都是确定性的，但**"一次全新真实 run 的 live vs persisted 对照"仍是空白**。
2. **投影是有损的**（5 个键）。想看 `checks` / `witnesses` / `uncited_candidates` 全量，仍需读 `claim_audit` 或 `synthesis_audit.json`。这是有意的取舍：全量内联会让 `synthesis.json` 涨约 14 倍。
3. **19 / 23 个历史产物没有 `finding_counts`**（早于 D2 或该 run 无 findings）。它们能正常解析、不报错，但无法做"历史 vs 重建"的计数对比 —— 已如实列出，未当成通过。
4. **`claim_support` 仍只做数值 / 单位 / 年份匹配**，不做语义判断。一条语义相悖但数字巧合的引用仍会被判 `supported_by_citation`。这是既有设计约束（避免 LLM Judge），本次继承未改。
5. **`agent_restatement` 未单列计数键**（落入 `unverified`），语义正确但粒度不如 `agent_consensus` / `derived`。属可选增强，非阻塞。
6. **`supported` 语义收紧会让新运行的对外数字下降**（例如旧的 9/10 → 8/10、10/14 → 4/14）。这是正确方向，但 v0.6.2 发版说明若引用该指标，措辞必须同步更新。
7. **`synthesis.json` 体积会小幅增加**：在 10-findings 的真实产物上实测约 +1.9 KB（≈194 B/finding）。

### 附带更正

AT-AUDIT-004 报告 `validation/AT-AUDIT-004-fix-report.md` 的 Known Limitation #1 写"support_audit 未被持久化 → `citation_verified` 恒为 0"。经本次追查，**该描述不准确**：完整审计一直在 `synthesis.json → claim_audit[]` 中。真实缺口是"**未挂在 finding 行上，导致行不自包含、按自然读法会静默丢掉 `citation_verified`**"。已在 §2.1 更正，并保留 `claim_audit` 回落路径作为向后兼容机制。
